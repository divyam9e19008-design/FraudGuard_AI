The retrieval pipeline
Eight stages between a typed question and a cited answer. The two retrievers run independently and only meet at the blend — which is the whole point of the design.
Each score array is normalised before blending, not after. BM25 returns unbounded term-frequency scores while cosine similarity is bounded to [-1, 1] — summed raw, BM25 would decide every result on its own and the semantic lane would be decorative.
The corpus
Six documents written as internal fraud-prevention policy. Each is split on its numbered headings, so a retrieved chunk is always a complete, quotable section rather than an arbitrary window of characters. The purpose line under each title is quoted from that document’s own “1. Purpose” section.
Chunking rule: re.split(r'\n(?=\d+\.\s)') — splits at a newline followed by “N. ”. Sub-numbered clauses like 3.1 stay attached to their parent section because the digit after the dot is not whitespace. Total across all six: 31 sections, which is exactly what the index holds.
Why two retrievers, not one
Each one fails in a way the other covers. Both examples below are real rows from the runs on this page — the component scores show one lane rescuing a section the other had nearly discarded.
BM25 · keyword
Carries the section when the words line up

Scores term overlap against the section text. It wins when the question names a field or phrase that appears verbatim in policy, and it is unbeatable on rare exact tokens that embeddings smooth away.

“high value application from a new device”
→ 05_escalation_procedure · 1. Purpose
BM25 1.000   MiniLM 0.739   fused 0.869
keyword lane ranked it first; the embedding lane did not
MiniLM · semantic
Rescues the section the keywords miss

Encodes the question into 384 dimensions and compares by cosine similarity. It wins when the wording differs entirely from the policy text — which is how investigators actually phrase questions.

“…no address history and comes from a new device”
→ 02_device_session_risk_policy · 2. Background
BM25 0.437   MiniLM 0.990   fused 0.714
the section never says “new device” — BM25 nearly dropped it
When both retrievers rank the same section first, the blend hands it a fused score of exactly 1.000, because each array is min–max normalised to a maximum of 1 before being averaged. A top score below 1.000 therefore means the two disagreed on first place — a free diagnostic, readable straight off the number.

KNOWN LIMITATION · OPEN ITEM

Retrieval can miss the one section that answers the question.

Ask “How reliable is the risk score itself?” above and watch the evidence boundary. The governance document’s 2. Known limitations — the section that actually quantifies reliability, with the 1-in-6 precision figure and the ranking-versus-precision note — does not make the top 3. A device-policy section beats it at 0.727. The answer is still correctly grounded in what arrived, but it is grounded in the wrong three sections.

The same failure appeared in an investigation run: a query naming “high income applicant” did not retrieve the income-tiering policy, so the model reported that income was “not mentioned in the provided policies.” The guard behaved correctly both times; the retriever did not.

Cause: top_k = 3 over 31 sections with no reranking. A multi-part query splits its signal, and BM25 rewards sections that repeat the query’s common words rather than the ones that answer it. Documented fixes, in order: widen the candidate set and add a cross-encoder reranker; then decompose multi-factor queries into one retrieval per factor. Neither is implemented yet.

Engineering integrity
Three decisions on this page that were easier to get wrong than right.
🛡

“Not covered” is a feature, not a failure.

The system prompt permits exactly one fallback: if the retrieved sections do not answer the question, reply NOT_COVERED and stop. No general knowledge, no reasonable-sounding guess. A fraud assistant that invents a policy clause is worse than one that stays silent, because the invented clause reads exactly like a real one.

📊

Every score here was computed, not chosen.

Component scores were never logged in the notebook — only fused ones. Rather than back-fill a plausible split, the index was rebuilt and re-run: same chunking, same BM25Okapi, same all-MiniLM-L6-v2. The two notebook queries reproduced 1.000 / 0.714 / 0.634 and 0.869 / 0.745 / 0.706 exactly, which is what makes the rest of the numbers trustworthy.

🧹

Six of the 31 chunks are junk.

The header block of every document — title, department, “applies to” — is chunk 0 of its file. It carries no policy content, yet it is embedded and retrievable like any real section. That is 6 of 31 index slots earning their place purely by accident of the chunking rule.
